# 真机画面（模拟后台）的定位与同步契约 —— 对齐稿

> 2026-11-25 22:1x，冰河大人追问「为什么要做这个模拟后台」后重写。
> 上一版结论（把"补齐模拟屏"当可选增量）是**错的**，见 §4。

---

## 1. 我怎么理解这个模拟后台的存在

它有三个职责，按重要性排：

### ① 开发期的真机替身（主职责）

真机是 ESP32-S3 + ST7796S 3.5 寸竖屏 TFT（逻辑 320×480）。
改一次 UI 的代价是：改 C 代码 → 推 GitHub → CI 编译（几分钟）→ 等固件产物 →
**USB 接本机烧录** → 复位 → 看屏。迭代周期以小时计，而且每一轮都要人在机器旁边。

浏览器里的 320×480 canvas 屏显把这个周期压到分钟级：改完刷新就能看、能点、能演示。
**它是"还没拿到真机/不想为看一眼 UI 去烧一次板"这件事的答案。**

### ② 端云契约的验证器

它不是前端假动画。摇杆手势经 `app/device_bridge.py` 代发，走**真实**设备协议：
真实 HMAC 签名、真实 AES 信封、真实配额账本、真实 AI 路由、真实课表/学科包下载。
浏览器自己不碰密钥（明文 HTTP 下 `crypto.subtle` 不可用，且密钥不得出服务端 — 05 §定位）。

所以它是**唯一能在没有硬件的条件下跑端到端**的载体。e2e 自检脚本测的是同一套契约。

### ③ 给人的可见物

家长/孩子在网页上就能看到设备现在的样子：真实课表、学科包、电子书、天气、配额、
固件版本。不是示意图，是当前真实状态。

---

## 2. 由此推出的保真度契约（这是关键）

**模拟屏是固件 UI 的第二个实现。** 它的价值完全建立在"与固件一致"之上：

- 不一致 → 你看到的不是真机该有的样子，替身就失去意义；
- 开发期是唯一窗口 → **功能只加在固件里而模拟屏不动，等于这个功能纸面上完成、
  实际上没人能在没硬件时看到它**。

`doc/05` 与 `ALIGN-NOTES §9.6` 写的是同一件事：真机画面按 `03` 复现屏显与手势。
`03` 是真相源，固件和模拟屏都是它的实现。

> **我上一轮的错误**：我把"模拟屏没跟上"解释成"模拟屏本来就不是镜像，只是复刻"，
> 然后把补齐它当成"新增量、不是修 bug"，还开了一张独立建议卡。
> 那是**回避了保真度契约**。正确表述是：模拟屏没跟上 = **这一项交付没完成**。

## 3. 实测漂移面（这次真机画面落后于固件的全部地方）

| 缺口 | 固件 | 模拟屏 | 影响 |
|---|---|---|---|
| `PAGE_CITY` 城市选择 | 有（设置页第 8 项 → 12 城市） | **无** | 天气城市功能在模拟屏完全不可见；且模拟屏 bootstrap 不带 `city`，服务端 `storage/settings.json` 永远不存在 |
| 阅读子页 `PAGE_BOOK_MENU/TOC/JUMP` | 有 | **无** | 书架→目录→跳转这条链路在模拟屏走不通 |
| 防沉迷锁屏 `PAGE_BOOK_LOCKED` | 有（宵禁 + 每日上限） | **无**，且无任何护栏逻辑 | 防沉迷这块在模拟屏**整块缺失** |
| `fw_version` | `1.0.1` | 写死 `'v1.0.3'` | 模拟屏 OTA 页永远不提示升级 |
| 设置页条目数 | 8 项 | 6 项 | — |

`ALIGN-NOTES §9.6` 记的是"13 个页面全部落地"——那是**加 PAGE_CITY 之前**的状态。

## 4. 方向：人工守门 vs 单一真相源

| | 做法 | 成本 | 漂移风险 |
|---|---|---|---|
| **A** | 把"固件 UI 改动必须同批改模拟屏"写成硬规则 + 一份页面/条目清单对照表，CI 跑差异检查 | 低 | 靠 CI 报错兜住，不靠人记 |
| **B** | 页面结构（标题/条目/文案/布局）抽成一份 JSON 规格，固件与 canvas 都由它生成 | 高（要动固件 UI 结构 + 加代码生成） | 结构上消除 |

**我的判断**：先做 A，把这次的漂移面补齐并让 CI 能报出来；B 作为后续结构化改造。
理由：现在 UI 还在快速变期（一天两个功能），抽规格的时机没到；但 A 能把
"漂移"从"靠我记得"变成"CI 报错"，这比人守可靠。

## 5. 已决定：模拟后台是「长期并存的能力」

> **结论（2026-11-25 拍板）**：选**长期并存**。模拟屏不是真机出来就删掉的临时替身，
> 而是固件 UI 的**第二个实现**，长期保留并持续跟进固件。

三个角色长期同时成立：

| 角色 | 长期含义 |
|---|---|
| 开发期真机替身 | 固件迭代期没板子也能看「屏幕长什么样」，改 UI 不必烧录；固件稳定后**依然保留** |
| 端云契约验证器 | 长期跑上报链路（心跳 / 天气 / OTA），持续验证端云字段口径一致 |
| 可见状态入口 | 家长/孩子在网页上长期看到设备当前真实状态 |

### 由此确定的工作机制

1. **同批更新是硬规则**：固件 UI 发生任何变化（新增/删除/改名页面、增删改设置项、改候选城市、
   改版本号），**必须在同一批次里同步修改模拟屏**；两批之间不允许存在任何中间状态。
2. **机器兜底，不靠人记**：由 `abbot/tools/check_ui_fidelity.py` 承担差异检查
   （页面集合 / 设置页条目 / 候选城市表 / 固件版本四项），CI workflow
   `.github/workflows/abbot-ui-fidelity.yml` 在 `push` / `pull_request` / 手动触发时跑它，
   **只改固件不改模拟屏的提交直接判红**。
3. **人只做初判**：CI 报红后由人判断是固件改对了（同步改模拟屏）还是模拟屏改错了（改回）。

### 本轮已落地的结果

* 模拟屏已与固件 1.0.1 逐页对齐（补齐 `PAGE_OOBE` / `PAGE_CITY` / `PAGE_BOOK_MENU` /
  `PAGE_BOOK_TOC` / `PAGE_BOOK_JUMP` / `PAGE_BOOK_LOCKED`），设置项与候选城市表已对齐，
  `fw_version` 与固件一致（`1.0.1`）；
* 保真度门禁已上线并全绿（`python3 abbot/tools/check_ui_fidelity.py` → 四项全 PASS，退出码 0）；
* 契约与门禁的完整说明见 `abbot/doc/07-模拟屏保真度与CI门禁.md`。

原问题里的两档取舍已由上面这条结论统一：**不再区分「开发期退役」档**，
A（CI 差异检查）覆盖 `03` 全文的页面与条目，不只查已发布功能。
