### 关键教训（下次照抄）
1. **CI 主机侧测试原来是 `set +e`** —— 链接失败被静默吞掉，`test_net_dispatch` 从来没真跑过。
   已改 `set -e`。以后新增主机侧测试务必确认 CI 真的在把关。
2. **host stub 只能写真机真实存在的名字**；漏一个桩 CI 就链接失败（这次是我漏了
   `net_sync_pending_assets`，被 `set +e` 掩盖了很久）。
3. **C++ UI 文件只有 CI 能编译**（本机无 LVGL）。为这类拼写错加了一道本机自查：
   收集 include/ 下所有头文件定义的宏/函数/类型/枚举成员，扫 src/ 与 test/ 里
   「用了但没定义」的标识符 —— 不用等 CI 就能发现同类错（枚举成员与文件内私有
   `#define` 会误报，但真错会直接暴露）。
4. **CI 失败只能读 `ci-logs` 分支**（本机拉不到 Actions logs/artifacts）：
   `git fetch origin '+refs/heads/ci-logs:refs/remotes/origin/ci-logs'` 后
   `git show origin/ci-logs:build-<sha>.log`。
5. **`nc_aes_ctr_crypt` 返回的是「输入 XOR 密钥流」** —— 造测试密钥流时输入必须是全 0，
   否则拿到的是噪声。
6. **局部块解密：密文必须摆在 `block[byte_in_block]`**，摆 `block[0]` 会让块尾用错密钥流
   （本块最后一个字节解成垃圾，肉眼极难发现，靠往返单测才抓到）。
7. **服务端 `pack_builder.py` 的 `DEMO_KEY` 原本是 17 字节**（`b"STUDY_DEMO_KEY_16"`），
   AES-128 要恰好 16 → `key_type="demo"` 的打包会直接抛 `Invalid key size`。
   仓库里唯一的包是 device 类型，所以这条路从没被走过。已改 `b"STUDY_DEMO_KEY16"`，
   固件常量与 doc/04、doc/05 同步；改完实测 demo 包构建成功。
   → **教训：固定密钥/常量要有一条「长度对不对」的自检**，光看名字像 16 字节没用。
8. **固件「已配对」真相源是 NVS 有没有 `device_secret`**，不是 TF 卡 `profile.json` 的
   `paired` 字段 —— 固件从不写那个字段（空白卡自愈生成的那份压根没这个键）。
   取两者「或」，否则自动登记成功后首页仍误报「还没连上学习助手」。
9. **doc/04 §2.2 曾声称空白卡自愈会预置 `/subjects/demo_pack/`** —— 固件实际只建目录与
   默认 JSON。已改文档为如实描述（学科包由网关心跳下发）。

不是绝对码位。证据：LVGL v8.3.11 `src/font/lv_font_fmt_txt.c` 的 `get_glyph_dsc_id()`：
```c
uint32_t rcp = letter - fdsc->cmaps[i].range_start;
uint16_t key = rcp;
uint16_t * p = _lv_utils_bsearch(&key, fdsc->cmaps[i].unicode_list, ...);
```
按相对码位重算，旧字库里本来就有上/一/三，只是没有北/京/气/市/℃。
→ 教训：查 LVGL 字库覆盖率必须先减 `range_start`，别信「grep 不到就是没有」。

## 固件 OTA 客户端代码审查发现一处误导性注释（待下一提交修）

`firmware/src/net/ota_client_esp.cpp:527-531` 写着：

> 写在 `esp_ota_end()` **之前**：`esp_ota_end()` 会把启动分区切到新分区

**这句是错的**（已对 ESP‑IDF 4.4.4 `components/app_update/esp_ota_ops.c` 逐行核对）：
`esp_ota_end()` 只做「校验镜像 + 结束写入」，**不切启动分区**；切分区的是 `esp_ota_set_boot_partition()`
（同文件 544 行，**代码本身是对的**）。不改的后果：后来人照注释删掉 `esp_ota_set_boot_partition()` →

顺带核实的两处**行为正确**（不要动）：
- `esp_ota_get_next_update_partition(NULL)` 传 NULL 是对的：IDF 内部 `start_from = esp_ota_get_running_partition()`，
  返回「另一个」OTA 分区（app0→app1，app1→app0，跑 app1 时循环落空回落到 `default_ota`=app0）。
- `ota_revert_to_previous()` 用同一个调用拿「上一版」也成立：只有在跑新分区（tag 匹配）时才会走到回滚分支，
  此时返回的正是旧分区。

## OTA 回滚保护的悬案查清了（18:50-19:00）

之前挂着的一个问题：「Arduino ESP32 核心会不会在 `setup()` 之后自动调 `esp_ota_mark_app_valid_cancel_rollback()`，导致核心提前标 VALID、崩溃后不能回滚？」—— **答案是不会，而且固件当前的写法也不依赖这一点**。

- **CI 探针给出直接证据**（`ci-logs` 分支的 `framework-ota-probe.txt`，由 OTA 子会话往 workflow 里加的探针步骤产出）：
  - 框架版本 `framework-arduinoespressif32 3.20017.241212`（基于 ESP‑IDF 4.4.4）。
  - 探针对 `cores/esp32/main.cpp` 做的 `grep -i -E 'ota|rollback|mark_app_valid|pending_verify|verify'` **匹配数为 0** → 核心的 `main.cpp` 里**没有任何 OTA/回滚相关代码**，更不会自动 mark valid。
  - `sdkconfig`：`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` + `CONFIG_APP_ROLLBACK_ENABLE=y`，`ANTI_ROLLBACK` 未开 → **bootloader 级回滚是开着的**，只要 app 不确认有效就会回滚。
- **固件侧写法（`src/net/ota_client_esp.cpp:682` `ota_boot_selfcheck_run()` + `src/main.cpp:110`）**：
  - 在 `setup()` 里**阻塞执行**（setup 不返回 → Arduino 那条自动 mark 路径根本没机会插手，即使核心有的话）。
  - 三条件全过才 mark：外设初始化成功 + 稳定 20 秒 + `task_ui_fsm` 心跳 ≥ 50；否则 `ota_revert_to_previous()` 指回旧分区。
  - NVS 记「待验证」标记 + 分区 tag + 尝试次数；连续自检失败超上限直接退回旧版，绝不刷成砖。
  - 回滚后能识别「当前跑的是旧版本」并清标记、显示「新版本自检未通过，已退回原版本」。
- **ESP‑IDF 4.4.4 源码核对**（`components/app_update/esp_ota_ops.c`，与本板 IDF 版本一致）：
  - `esp_ota_get_next_update_partition(NULL)` → `start_from = esp_ota_get_running_partition()`，返回**另一个** OTA 分区（app0↔app1）；跑 app1 时循环落空会回落到 `default_ota`（app0）。**传 NULL 是对的**，`f75eebf` 的修法正确。
  - `esp_ota_begin()` 会拒绝两种情形：写**正在运行的**分区 → `ESP_ERR_OTA_PARTITION_CONFLICT`；运行中的 app 处于 `PENDING_VERIFY` → `ESP_ERR_OTA_ROLLBACK_INVALID_STATE`。
