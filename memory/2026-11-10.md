## 出口代理下取远端提交的两个有效手段 <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->

走出口代理 `git fetch` 报 `RPC failed; curl 16 The requested URL returned error: HTTP2 framing layer`，
走直连（unset 代理变量）有时报 502。两下都能绕开的写法：

```bash
# 1) 强制 HTTP/1.1，避开 HTTP2 分帧问题
env -u HTTPS_PROXY -u HTTP_PROXY -u ALL_PROXY -u https_proxy -u http_proxy -u all_proxy \
  git -c http.version=HTTP/1.1 fetch --no-tags origin <sha>

# 2) 按对象取，不是按分支取 —— 分支名 fetch 要列远端 refs，容易被代理打断；
#    直接给 SHA 往往能成。
```

三次重试里第三次成功的概率不低，失败就重试而不是换方案。拿到对象后用
`git update-ref refs/remotes/origin/main <sha>` + `git reset --hard <sha>` 对齐，
不要用 `git reset --hard origin/main`（origin/main 还指着旧提交）。

**推 API 侧**：7 个文件这种量级，树 API 分块（每块 3 条，逐块以上一块的 tree 当 base_tree）能过；
分块后最终 tree 与本地 `HEAD^{tree}` 一致即算推送成功。本轮用 `/tmp/push_license.py` 验证过。

### 屏幕亮度（软件压暗）—— 已上线 <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->

远端提交 ba2922851868545297669ca8b7600ab9c4746a1a，CI 全绿。

**为什么做软件压暗而不是硬件调光**：这块屏是透射式 TFT（ST7789），背光 BL 直接接 3.3V、
硬件上没有开关、没有 PWM。要调背光得加 MOSFET 改接线 —— 冰河大人明确说「涉及硬件改造就没有意义」。
所以走软件：像素画得越暗，透过去的光越少。压不掉的是背光漏光底噪（全黑时屏仍是个微灰方块）。

**实现要点**：
- 压暗必须在**线性光**里做（sRGB → 线性 → ×k → sRGB）。直接乘 sRGB 数字会把暗部压过头、颜色跑掉。
- 落点 petd/render.py，三个渲染入口（主帧 / 内容卡 / 照片卡）都接 dim 参数。
- **顺序：压暗在防烧屏之前**。反过来的话 ±4 色阶会被压暗曲线吃掉（30% 档只剩 ±1.8）；
  而且满亮度时白底 +4 会先被截断在 255，压暗后不再截断，防烧屏才真的在工作 —— 顺手修掉一个隐性问题。
- 档位：自动（夜里 50%、白天不压，跟睡觉时段走）/ 100 / 70 / 50 / 30。纯服务端，固件零改动。
- 配置 ui.brightness 默认 auto；认不出来的值一律当 auto（宁可夜里暗一点，别半夜突然亮起来）。

**踩坑**：测试抓到 brightness_factor 对未知值返回 1.0，而它自己的文档写的是「认不出来就当自动」——
实现和意图不一致。改成显式回退到 auto。这条测试有推翻力（真 bug）。

**实测（后台 preview.jpg 抓真实帧）**：
100% 平均 134.68 / 70% 114.18 / 50% 97.42 / 30% 76.04 —— 单调下降。
sRGB 中灰 135 在线性光减 70% 后理论值 76，实测 76.04 吻合；
若是「直接乘 sRGB 数字」会是 67 —— 差 9 个色阶，所以曲线实现可证是对的。

**踩坑2**：preview 路由是 /admin/api/preview.jpg，写成 /preview 拿到的是 404 文本，按图片打开会报
「cannot identify image file」。

**没验证的**：屏上看着到底还刺不刺眼 —— 人的判断。设备跑 fw 0.4.7 旧固件，
但压暗是纯服务端的（设备只收整帧 JPEG），所以立刻生效，不刷机。

### 大文件推 GitHub 的通用做法 <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->

推 tree/blob 时按体积选路子：

node = jr.ComponentNode(kind='text', props={'font_size':9}, content='', children=[])

## 关键纠正：逻辑层 ≠ 执行层（冰河大人 16:07） <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->

我一直拿「引擎缺什么原语」去否决玩法 —— 那问的是执行层，我却当成了逻辑层的能力清单。
纸牌接龙的「花色交替、降序、能不能放那堆」根本不需要引擎懂 —— 那些规则写在**生成 pack 的程序**里。

三层划分：
- **逻辑层**：生成器（服务端 Python 写 pack）—— 任意规则、比较、状态、每局不同的随机牌局
- **表达层**：pack（规则表+实体+图样）—— 受 12 实体 / 24 规则 / 8 色 / 32×16 图样格 预算约束
- **执行层**：固件引擎 —— 渲染、输入采集、碰撞、事件路由

真正的天花板不是「17 种原语」，是**表达层的预算**，其中最硬的是 12 个同时可见对象。

**状态可以空间化**：用 marker 实体的位置表示「当前状态」—— marker 压在哪张牌上，
哪条规则就命中。这样引擎不需要有状态概念，「翻回」「当前选中」都能用原语拼出来。

## 翻牌消消：6 张还是 8/10 张（16:27→17:31 讨论中） <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->

我算错了对象：6 是「几何重合当布尔运算 + 组合规则展开」这套**编码**的上限，不是平台上限。

- 组合规则展开：C(n,2) 条 hit 规则 → 6 张=15 条，8 张=28 条，超 24 规则上限
- 6 张 3 对的摆法：6 个 mask + 1 光标 + 4 个配对指示 = 11 实体（余 1）
- 核心机制：翻开的 mask 都移到同一个「弃牌堆」→ 物理重叠 → 引擎发 hit →
  生成器为每种组合预写规则 → 是配对就消掉、不是配对就各自回家。**自动翻回**就是这么来的
- 省规则技巧：不匹配的回翻用**一条 timer 规则 + 6 个效果**（各自 set_pos 回原位），
  而不是 12 条组合规则。副作用是它无条件周期触发 ⇒ 间隔设成「翻第二张牌的时间限制」，反而变成玩法
- 通关判定是唯一真难点：empty 用不上（pattern 里压着牌面图案，永远清不空）⇒

## 翻牌消消：「6 张」是我算错的，不是平台上限（2026-11-10 18:15） <!-- project: path:/home/open/.openclaw/workspace/ai-agent-pet -->
